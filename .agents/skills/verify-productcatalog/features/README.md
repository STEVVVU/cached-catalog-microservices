- `scripts/catalog-benchmark.py` runs real database/gateway processes with 9/500/5000 products, one/three gateways, no-cache/TTL/lease modes, 60-second/1ms TTLs and 100/1000/5000 offered requests per second. Five reversed-order repeats retain the 50% List, 40% Get, 10% Search mix and exact expected protobuf values. `catalogctl load` preserves scheduled arrivals, bounded workers/queue, rejections, status codes, timeouts, generator lag and raw latencies. A separate 60-second case restarts one gateway and the durable database while requests continue. CPU profiles require the separate `benchmark` build tag and profile workflow input.
- The next framework path is `python3 scripts/catalog-benchmark.py --k6 --output reports/evidence/k6`. It reuses the same process/fixture/restart driver and invokes the Go protobuf oracle before each trial. `scripts/catalog-k6.js` loads the repository's real `demo.proto`, uses native gRPC and constant-arrival-rate with a fixed 64-VU cap, and validates normalized protobuf fields. k6 supplies request/iteration/validation-group timing and dropped-iteration counts; no latency is inferred for dropped offers. Native summary and compressed granular JSON survive cleanup. `catalog-k6.yml` first defaults to a setup smoke; actual k6 execution remains the readiness gate until that run passes.
