# Native k6 catalog measurement

The next load path uses k6 2.3.0 for gRPC calls, open arrival scheduling, request timing and statistics. The existing Python driver owns only service processes, deterministic catalog fixtures, resources, restart actions and evidence. The Go client remains the exact protobuf oracle and existing profile reference. No browser, k6 Cloud, credentials or public listener is involved.

Run `node scripts/catalog-oracle.test.mjs` for field-normalization controls. The controls reject a changed product and swapped assignments while accepting protobuf integer/default representations. The manual `.github/workflows/catalog-k6.yml` defaults to `smoke=true`; a real Linux k6 smoke is still required before this path is considered proven. It builds the current Go services and runs `python3 scripts/catalog-benchmark.py --k6 --smoke --output reports/evidence/k6`. Set the workflow's smoke input to false for the frozen full workload.

Each k6 trial loads `protos/demo.proto`, keeps native gRPC connections per VU and gateway, and uses constant-arrival-rate with 64 preallocated VUs and a fixed 64-VU maximum. RPC deadlines are three seconds. The request mix is 50% List, 40% Get and 10% Search among started iterations. Every successful response must match the ordered, normalized protobuf fields. Correctness errors fail a threshold. RPC failures, explicit DeadlineExceeded responses, dropped offers and interrupted iterations are retained separately.

The framework reports high-resolution `grpc_req_duration` for status-zero RPCs. Native `iteration_duration` also includes first connection, validation and client orchestration. The validation group has its own native duration. Dropped offers have no latency value. A VU's started-iteration ordinal selects an operation and replica only; it never supplies a scheduled timestamp. The raw k6 summary, compressed metric-point JSON and actual versus planned offer counts remain available. This latency definition differs from the initial Go client's schedule-to-response duration, so cross-generator latency values are not a before/after service optimization comparison.

Sources inspected before implementation are Grafana's [native gRPC API](https://grafana.com/docs/k6/latest/javascript-api/k6-net-grpc/client/), [connection options](https://grafana.com/docs/k6/latest/javascript-api/k6-net-grpc/client/client-connect/), [constant arrival rate](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/), [built-in metrics](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/), [custom summary](https://grafana.com/docs/k6/latest/results-output/end-of-test/custom-summary/) and [compressed JSON output](https://grafana.com/docs/k6/latest/results-output/real-time/json/). The official setup action's `action.yaml` and verified commit `43b9fc21641a76002687994433dd586f56e791b1` were inspected. The action is Apache-2.0; k6 is AGPL-3.0 and runs as an external measurement executable. It is not linked into the catalog service.
