# Matched native k6 comparison

The complete matched campaign did **not establish a performance improvement or catalog service capacity**. It completed all 1,086 trials and exact-response assertions, retaining substantial overload failures and dropped arrivals. The copy-outside-lock candidate remains a bounded critical-section change; this run supports no general speedup claim.

[Run 39769299508](https://github.com/STEVVVU/cached-catalog-microservices/actions/runs/39769299508) measured source `261efc6f92d6dd846c0dbe7bf899ca7f7057b9b9` against frozen baseline `a0bd7a086fab59c81b73c00e4c3b8d0d62129a7c`. The four-logical-CPU Microsoft VM exposed an AMD EPYC 9V45, 16,760,344,576 bytes RAM, Ubuntu/glibc 2.39 and Linux 7.0.0-1017-azure. Initial load averages were 6.23/2.40/0.89. This differs from the earlier Xeon campaigns; their measurements are separate. Go was 1.27.3 and native k6 was 2.3.0, commit `e088784614`.

## Work and acceptance

Each build ran 108 ordinary groups, five times each: 9/500/5,000 products, one/three gateways, 60-second/1ms TTL, 100/1,000/5,000 scheduled iterations per second, and none/TTL/lease modes. Each ordinary trial lasted six seconds. Six interleaved build/mode arms reversed order on odd rounds, each with fresh owned services and database. Six additional 60-second trials used 500 products, three gateways, 50ms TTL and 1,000 offers/s, restarting one gateway and then the durable database. Their twelve restart actions and readiness times are retained.

The actual gRPC mix was 50% List, 40% Get and 10% Search among started iterations. Each response was normalized and compared with the frozen expected protobuf fields before incrementing the successful counter. A separate Go exact oracle passed before every trial. Cache correctness requires zero response mismatches; deliberate restarts and overload do not excuse incorrect successful responses. Availability errors, deadlines and unsent iterations remain separate outcomes.

Both normal servers used independent build caches, `-trimpath -buildvcs=false`, identical embedded dependencies/settings and distinct binaries. Runtime source inventories matched; only `catalog_cache.go` differed, moving defensive copies outside the cache mutex while retaining immutable snapshots, expiry and invalidation logic. Six workload/dependency inputs and all catalog hashes matched. Main additionally checked 34 runtime source hashes and six fixed-input hashes against the exact Git blobs. No profiling or race instrumentation was in the timed binaries.

Native RPC duration excludes connection and post-response validation overhead. Whole started-iteration and validation-group durations are retained separately. Dropped arrivals have no invented latency. The fixed 64-VU generator, gateways and database shared four logical CPUs; iteration work includes decoding and exact validation. Drops occurred in 353 baseline and 355 candidate trials. This complete setup did not sustain many configured arrival rates. The limiting component was not isolated, so the drop rate does not establish the catalog service's independent capacity. [Grafana documents these arrival-rate/VU limits](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/dropped-iterations/).

Resource samples show substantial generator pressure. In the pre-existing 500-product/one-gateway/60s-lease/1,000-offer/s case, the ten baseline/candidate trials accumulated 22.40–22.55 sampled generator CPU-seconds and 1.14–1.23 gateway CPU-seconds over 6.01–6.51-second observation intervals. Those first-to-last per-PID CPU ticks put most observed CPU consumption in the generator on this four-logical-CPU host. They do not isolate validation, decoding, initialization or the cause of each late request. Role RSS and CPU observations are retained per trial; sampled single-process RSS is distinct from physical peak memory or a simultaneous process-tree peak.

## Native duration coverage issue

In 35 trials, all with 5,000 products, native status-zero duration counts fell below custom successful-operation counts by 37 samples: 14 baseline and 23 candidate. Raw metric streams confirm the same omission. Fifteen affected trials had no reported failures or explicit deadlines. The [retained coverage list](../evidence/matched-k6-20261022/summary.json) identifies every affected cell. No missing duration was filled, reclassified as a failure, or removed from its outcome total.

Consequently, affected percentiles describe **recorded successful-RPC duration samples**, with incomplete coverage of successful calls. The small aggregate gap does not prove unbiased missingness or protect each trial's tail estimate. Missing-duration causes remain unconfirmed. The pinned framework's [gRPC stats handler](https://github.com/grafana/k6/blob/e088784614/internal/lib/netext/grpcext/conn.go#L259) uses context-sensitive metric emission; its [sample helper](https://github.com/grafana/k6/blob/e088784614/metrics/sample.go#L119) can skip a sample after context cancellation. This is a possible mechanism, not a controlled diagnosis of these particular omissions.

After the campaign, the Python mapper was extended to retain `native_status_zero_count` and `native_duration_gap` explicitly. Both new fields were checked against all 1,086 retained native summaries. Product code, scheduling, timing, fixtures and raw campaign records were unchanged. A new controlled telemetry diagnostic is required before attributing the cause; an unchanged full rerun would not resolve it.

## Evidence and scope

The [curated evidence](../evidence/matched-k6-20261022/summary.json) includes source/build identities, all counts, restart actions, coverage gaps and hashes of every native summary, oracle receipt and compressed stream. The full 646,228,813-byte hosted artifact and 160,011,109-byte result remain in the local metrics evidence store, alongside the earlier failed campaigns. GitHub's published ZIP digest is recorded as metadata; extracted receipt contents and hashes were independently audited. See [the setup-failure record](2026-10-22-matched-setup-failure.md) for the two distinct port-allocation failures and their regression fixes.

The separate native profile located full-catalog cloning under the cache mutex, but used a different runner and instrumented binary. Its timing is excluded here. The selected comparisons have overlapping ranges, substantial drops at higher rates and unresolved latency coverage in some large cases. These limits support the inconclusive verdict; no 1.2K-RPS/186-to-104ms claim or 52% six-service gain follows. Only the catalog path was measured, and the complete eleven-service storefront and autoscaling were not deployed in this experiment. Finite race/restart checks are useful mechanism evidence, not a universal correctness or reliability proof.
